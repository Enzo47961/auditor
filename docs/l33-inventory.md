# L-33 — inventory of user code executed during elaboration (Phase 1)

```
source: leanprover/lean4 v4.36.0-rc1 (commit c9afcddf), Mathlib e1b2403b; citations generated from the pinned source
classification: author-self-review (L-26)
```

"Instruction N" refers to the numbered decisions of the project's external reviewer.

**Question.** Which tactics, terms, commands and attributes execute **user** code during the elaboration of a file, before Stage B sees the environment? The criterion is that of L-17, amended by L-33a: it applies to a command, tactic, term or attribute.

**Scan.**
- Expressions searched for in Lean's source (`Lean/`, `Std/`, `lake/`): `evalExpr`, `evalExpr'`, `evalTerm`, `evalConst`, `evalConstCheck`, `runTermElab`, `runCommandElabM`, `addAndCompile`.
- The same expressions in Mathlib.
- Also the attribute registrations (`registerBuiltinAttribute`, `KeyedDeclsAttribute.init`, `mkElabAttribute`, `registerInitAttr`).
- For each evaluation point, we identified the user syntax that triggers it.
- Raw list: 232 lines, kept in the maintainer's working directory (`l33/grep_eval.txt`).
- The citations below were generated by a script from the pinned source, not copied by hand (the independent-review rule, `roadmap.md`).

**Three ways for user code to get executed:**
1. **At the point where it appears.** The code is evaluated and discarded (`withoutModifyingEnv`), so only the text reveals it. Defence: **lexical**.
2. **Registered in the environment and executed later.** An attribute registers the user's declaration as an elaborator, tactic, simproc, linter, `init`, etc., and the elaborator runs it when the situation arises. The declaration stays in the environment with a type that reaches `IO.RealWorld`, since every metaprogramming monad is built on `EIO`. Defence: **from the environment**, in Stage B.
3. **A user term evaluated as data.** This is the case for tactic configuration, `include_str`, `autoParam`, `eval%` and widgets. A pure term does no IO. To do so, it needs an escape hatch:
   - `unsafe` (lexical);
   - `@[extern]` (from the environment);
   - `implemented_by` pointing to an `unsafe` implementation (lexical, through the `unsafe`);
   - code from another file of the PR (dependency, below).

## Implemented decisions (Stage A v4, inspector v5)

| Mechanism | Defence | Result |
|---|---|---|
| `run_tac`, `by_elab` in the file | lexical, in any position (`elaboration_code_execution`) | **`Rejeitada`** (rejected): the execution is a concrete violation (`elaboration_executes_code`, in `policy_violations`) |
| `unsafe` in the file (modifier or term) | lexical, in any position (`unsafe_code`) | `Não resolvida` (unresolved; `stage_a_unrecognized`) |
| A constant of the target module whose **type** reaches `IO.RealWorld`, or that carries `@[extern]` | **from the environment** (inspector v5, `execution_capable`) | `Não resolvida` (`target_defines_executable_code`). Registering does not prove that it executed |
| A file changed in the PR, imported by the target, with `run_tac`/`by_elab` (or unreadable) | lexical in the changed file + the inspector's `imports`; `auditor-ci` passes the changed files (`--changed`) | `Não resolvida` (`dependency_executes_code`) |
| `show_panel_widgets` | core classification: it was `allowed`, it became `metaprogramming` (classification v5) | `Não resolvida`, like `#widget` |
| Commands that evaluate code (`#eval`, `#guard`, `#widget`, `run_cmd`…) | classification (L-17), already fail-closed | `Não resolvida` |
| Native evaluation (`native_decide`, `decide +native`) | Stage B (Q9) | `Rejeitada` / `Não resolvida`, as before |

**What stays outside the lexical and environment defences, and why:**
- **Code from a dependency not changed in the PR.** It is Mathlib or another library at the pinned commit, already reviewed on the base branch. The same premise as the libraries' TCB.
- **Code from Mathlib's external dependencies.** Batteries, Aesop, Qq, ProofWidgets, Plausible, LeanSearchClient and importGraph **have not been inventoried**: only the core and Mathlib have. Declared in L-33a.
- **A changed dependency that registers code (through 2 or 3) without `run_tac`/`by_elab`.** It is audited as a target, and comes out `Não resolvida` (`target_defines_executable_code` or `unsafe_code`). The target that imports it does **not** inherit the flag: the dependency crossing only uses the lexical finding. Declared in L-33a.
- **A `lakefile.lean` changed in the PR.** Lake executes code from the configuration (``lake/Lake/Load/Lean/Eval.lean:130``). It is outside the reach of Stage A, which audits the project's modules.
- Against **any** mechanism not inventoried, the defence is the structural mitigation (b) of instruction 24: hashing the inspector and the auditor before and after `lake build` (`roadmap.md`).

## 3. Attributes that register the user's declaration (from the environment)

- The type of these declarations (`Tactic`, `TermElab`, `CommandElab`, `Macro`, `Simproc`, `Parser`, `IO Unit`, `NormNumExt`…) reaches `IO.RealWorld`.
- This is detected by inspector v5 (`execution_capable`), without a list of attribute names. Syntax names differ from the registered ones (for example, the attribute registered as `PolyInferBaseAttr` is written `polynomial_infer_base`), and a lexical list would be fragile.

**`initialize`, the reviewer's question 2.** The attribute's documentation says that "Initialization procedures are run in files that import the file they are defined in". `runInitAttrForMod` walks the **imported** modules. Scenario 10 (ground truth) checks both halves by execution on the pinned toolchain:
- compiling the file that declares `initialize` does not run it;
- compiling a file that imports it does.

Consequences:
- In the **target**, the `initialize` procedure is an `IO …` constant of the module, so inspector v5 flags it (`target_defines_executable_code`). In addition, the command remains `metaprogramming`.
- In a **dependency changed in the PR**, `initialize` runs during the target's build, and the lexical defence of the dependency crossing does **not** catch it (only `run_tac`/`by_elab`). Declared in L-33a; covered only by mitigation (b).
- That is why no reclassification of `initialize` as `allowed` is applied.

## 4. User terms evaluated as data

They execute user code only through an escape hatch (lexical `unsafe`, `@[extern]` from the environment) or through dependency code.

- **Tactic configuration** (`simp (config := e)`, `+option`): the elaborators generated by `declare_config_elab` evaluate the elaborated configuration with `evalExpr'` in `unsafe` mode. `Lean/Elab/Tactic/Config.lean:150–151`

      Meta.evalExpr' (safety := .unsafe) $type ``$type e
